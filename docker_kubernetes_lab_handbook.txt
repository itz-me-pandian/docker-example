2. DOCKERFILE TEMPLATES

2.1 Node.js application
-----------------------
Expected files:
  server.js
  package.json
  Dockerfile

server.js:
-----------
const http = require('http');

const server = http.createServer((req, res) => {
  res.writeHead(200, {'Content-Type': 'text/plain'});
  res.end('Hello from Docker Node.js!');
});

server.listen(3000, '0.0.0.0', () => {
  console.log('Server listening on port 3000');
});

package.json:
-------------
{
  "name": "docker-node-lab",
  "version": "1.0.0",
  "private": true,
  "scripts": {
    "start": "node server.js"
  }
}

Dockerfile:
-----------
FROM node:22-alpine
WORKDIR /app
COPY package*.json ./
RUN npm install --omit=dev
COPY . .
EXPOSE 3000
CMD ["npm", "start"]

Build and run:
--------------
docker build -t node-lab:1.0 .
docker run -d --name node-lab -p 3000:3000 node-lab:1.0
docker logs node-lab
# Test http://localhost:3000
docker stop node-lab
docker rm node-lab

2.2 Python Flask application
----------------------------
app.py:
-------
from flask import Flask
app = Flask(__name__)

@app.route("/")
def home():
    return "Hello from Docker Flask!"

if __name__ == "__main__":
    app.run(host="0.0.0.0", port=5000)

requirements.txt:
-----------------
flask

Dockerfile:
-----------
FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
EXPOSE 5000
CMD ["python", "app.py"]

Build/run:
----------
docker build -t flask-lab:1.0 .
docker run -d --name flask-lab -p 5000:5000 flask-lab:1.0
# Test http://localhost:5000

2.4 Dockerfile instruction meanings
-----------------------------------
FROM       Base image
WORKDIR    Working directory inside the image
COPY       Copy files from build context into image
ADD        Copy files; also supports URL/local archive behavior. Prefer COPY for normal copies.
RUN        Execute a command while building the image
ENV        Set environment variable
ARG        Build-time variable
EXPOSE     Document the intended listening port; does not publish it
CMD        Default command/arguments when container starts
ENTRYPOINT Main executable for the container
USER       Set runtime user
VOLUME     Declare a mount point
HEALTHCHECK Define a health check

3. DOCKER COMPOSE
============================================================

3.1 Node app + Redis example
----------------------------
docker-compose.yml:
--------------------
services:
  app:
    build: .
    container_name: node-app
    ports:
      - "3000:3000"
    environment:
      REDIS_HOST: redis
    depends_on:
      - redis
  redis:
    image: redis:7-alpine
    container_name: redis
    volumes:
      - redis-data:/data

volumes:
  redis-data:

Commands:
---------
docker compose up
docker compose up -d
docker compose up --build -d
docker compose ps
docker compose logs
docker compose logs -f app
docker compose exec app sh
docker compose stop
docker compose start
docker compose down
docker compose down -v
# down -v also removes Compose-managed named volumes; data may be lost.

3.2 Web + database template
---------------------------
services:
  web:
    build: .
    ports:
      - "8080:3000"
    environment:
      DB_HOST: db
      DB_PORT: "5432"
      DB_NAME: labdb
      DB_USER: labuser
      DB_PASSWORD: change-me-for-local-lab
    depends_on:
      - db
  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_DB: labdb
      POSTGRES_USER: labuser
      POSTGRES_PASSWORD: change-me-for-local-lab
    volumes:
      - postgres-data:/var/lib/postgresql/data
volumes:
  postgres-data:

Note: This is a classroom template, not production secret management. Do not commit real
credentials. depends_on controls startup order but does not by itself guarantee database readiness.

7.2 Deployment
--------------
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-deployment
spec:
  replicas: 2
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
        - name: web
          image: nginx:alpine
          ports:
            - containerPort: 80

Commands:
kubectl apply -f deployment.yaml
kubectl get deployments
kubectl get pods -l app=web
kubectl scale deployment web-deployment --replicas=3

7.3 Service (NodePort)
----------------------
apiVersion: v1
kind: Service
metadata:
  name: web-service
spec:
  type: NodePort
  selector:
    app: web
  ports:
    - port: 80
      targetPort: 80
      nodePort: 30080

Apply:
kubectl apply -f deployment.yaml
kubectl apply -f service.yaml
kubectl get svc
minikube service web-service

Service types:
ClusterIP  Internal cluster access; default
NodePort   Exposes a port on each node
LoadBalancer Requests an external load balancer from supported infrastructure

7.9 Liveness and readiness probes
---------------------------------
containers:
  - name: web
    image: nginx:alpine
    ports:
      - containerPort: 80
    readinessProbe:
      httpGet:
        path: /
        port: 80
      initialDelaySeconds: 5
      periodSeconds: 10
    livenessProbe:
      httpGet:
        path: /
        port: 80
      initialDelaySeconds: 10
      periodSeconds: 20

Readiness: whether a container should receive Service traffic.
Liveness: whether Kubernetes should restart a container that fails the check.

7.10 Resource requests and limits
---------------------------------
resources:
  requests:
    cpu: "100m"
    memory: "64Mi"
  limits:
    cpu: "500m"
    memory: "256Mi"

Requests are used for scheduling; limits cap resource usage.

7.11 Horizontal Pod Autoscaler (HPA)
------------------------------------
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: web-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: web-deployment
  minReplicas: 2
  maxReplicas: 5
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70

Needs resource requests and a functioning Metrics Server for CPU-based autoscaling.
Commands:
kubectl apply -f hpa.yaml
kubectl get hpa
kubectl describe hpa web-hpa
kubectl top pods

7.12 Ingress (controller required)
---------------------------------
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: web-ingress
spec:
  rules:
    - host: lab.local
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: web-service
                port:
                  number: 80

An Ingress resource alone does not provide an Ingress controller. Enable/install a compatible
controller (for example, Minikube's ingress addon) and configure hostname resolution if needed.

8. COMMON KUBERNETES WORKFLOWS
============================================================

8.1 Deploy an app
-----------------
1. Build or pull the application image.
2. Write a Deployment YAML.
3. Write a Service YAML.
4. Apply the files.
5. Check rollout, pods, events and logs.
6. Expose/test the Service.
7. Clean up when finished.

Example:
docker build -t my-app:1.0 .
minikube image load my-app:1.0
kubectl apply -f deployment.yaml
kubectl apply -f service.yaml
kubectl rollout status deployment/my-app
kubectl get pods -o wide
kubectl get svc
minikube service my-service

8.2 YAML validation and debugging
---------------------------------
kubectl apply --dry-run=client -f deployment.yaml
kubectl diff -f deployment.yaml
kubectl describe pod POD_NAME
kubectl logs POD_NAME
kubectl get events --sort-by=.metadata.creationTimestamp
kubectl get pod POD_NAME -o yaml

Common statuses:
Pending              Scheduling/storage/resource issue; describe pod
ImagePullBackOff     Wrong image/tag, registry access or imagePullSecret
CrashLoopBackOff     Application repeatedly exits; inspect logs and command
ErrImageNeverPull    Image missing on node with imagePullPolicy: Never
CreateContainerConfigError  Often missing ConfigMap/Secret/key or invalid config
Running but unreachable  Check Service selector, targetPort, app listen address, network

8.3 Useful selectors and output

kubectl get pods -o yaml
kubectl get deployment web-deployment -o wide
kubectl describe svc web-service

10. COMMANDS FOR WINDOWS POWERSHELL VS LINUX
============================================================

Most docker and kubectl commands are the same on Windows, Linux and macOS.
Differences commonly arise in paths, environment variables and shell syntax.

Linux/macOS:

cat file.yaml
cp source destination

Windows PowerShell:

Get-ChildItem
Get-Content file.yaml

On Windows, ensure Docker Desktop is running and Kubernetes/Minikube is configured.

11. COMMON EXAM MISTAKES
============================================================

Docker:
- `docker build` needs a build context, usually the final dot: `docker build -t app .`
- Use `-p HOST_PORT:CONTAINER_PORT`, not the reverse.
- `EXPOSE` documents a port; `-p` publishes it to the host.
- Use `WORKDIR /app`, not `WORKDIR .`, for a predictable working directory.
- `COPY . .` copies from the build context; ensure required files are present.
- `CMD` should be valid JSON-array syntax for exec form, e.g. CMD ["node", "server.js"].
- The application must listen on `0.0.0.0` inside the container, not only `127.0.0.1`.
- Ensure package.json has the expected start script.
- Do not bake real secrets into images.
- Check whether a container name already exists before reusing it.

Kubernetes:
- Deployment selector must match the labels in `spec.template.metadata.labels`.
- Service selector must match the Pod labels exactly.
- Service `targetPort` must match the application's container port.
- YAML indentation matters; use spaces, not tabs.
- `containerPort` does not itself expose a Service externally.
- A local image must exist on the Minikube node; use `minikube image load`.
- `imagePullPolicy: Never` fails if the image is absent on the node.
- A Service only routes to matching, ready Pods.
- HPA CPU scaling typically requires CPU requests and Metrics Server.
- An Ingress requires a controller.
- `kubectl apply -f file.yaml` creates or updates; `kubectl delete -f file.yaml` deletes.
- Avoid deleting namespaces, persistent volumes or data without checking impact.

12. QUICK EXAM MEMORY SHEET
============================================================

Docker image lifecycle:
  pull/build -> images -> run -> ps/logs/exec -> stop -> rm
  build -> tag -> login -> push
  pull -> run

Dockerfile order (typical):
  FROM -> WORKDIR -> COPY dependency files -> RUN install
  -> COPY source -> EXPOSE -> CMD

Compose:
  docker compose up -d
  docker compose ps
  docker compose logs -f
  docker compose down

Kubernetes workflow:
  kubectl apply -f ...
  kubectl get pods
  kubectl describe pod ...
  kubectl logs ...
  kubectl get svc
  kubectl rollout status deployment/...
  kubectl delete -f ...

Kubernetes object purposes:
  Pod          Runs container(s)
  Deployment   Manages replicas and rolling updates
  Service      Stable network endpoint for Pods
  ConfigMap    Non-sensitive configuration
  Secret       Sensitive configuration data (protect access; base64 is not encryption)
  PVC          Requests persistent storage
  HPA          Scales replicas from metrics
  Ingress      HTTP/HTTPS routing via an Ingress controller
  Namespace    Logical resource grouping
